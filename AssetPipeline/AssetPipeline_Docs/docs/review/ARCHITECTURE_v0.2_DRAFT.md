## 0. 유지하는 것과 더하는 것

**유지(합의됨):** 기존 `anim_gen` = 실행 평면 · Claude Blender Integration 기반 Blender MCP · Keyframe Coach 와 Blender Unreal Pipeline Skill 재사용 · 실행 위치(Blender / UE)는 Provider 속성 · 연산 기록(Operation Journal) · Headless Replay · 영속 체크포인트 · Blender 4.4 우선 유지 · UE 풀이기는 비교 기준이자 Provider.

**더하는 것(이 문서):**
1. Tool 을 부르는 자동화가 아니라 **관찰 → 진단 → 수정 → 평가를 스스로 도는 루프**
2. **신규 키프레임 애니메이션 제작**
3. 영상 기반 제작의 **네 경로**(A 직접 복원 · B 키 포즈 재생성 · C 차이 분석 후 수정 · D 영상 생성)
4. **메시 · 본 · 가중치의 자율 진단 · 보정**
5. 검증 기준 보완(파일 무결성 ↔ 의미적 동등성 분리 등)
6. GPL · AGPL 활용 판단

새 클래스 계층은 만들지 않는다. 루프의 주체는 Claude 이고, Core 에는 루프가 기대는 것 넷(체크포인트 · 연산 기록 · 평가 Tool · 시도 기록)만 더한다.

## 1. 자율 제작 · 수정 루프

### 1.1 흐름

```text
제작 목표(예: "이 공격 애니가 어색하니 자연스럽게")
   │
   ▼
① Scene Observation ── 씬 · 리그 · 액션 · 프레임 범위 조회
② Numerical Validation ── 수치 검사 묶음 → 기준선(before)
③ Visual Review ── 고정 조건(카메라 · 프레임)으로 시트 렌더 → 기준선 이미지
   │
   ▼
④ Error Diagnosis ── 문제 목록{코드, 근거(프레임 · 본 · 수치 · 이미지), 확신도}
   │        └ 측정 가능한 문제가 없으면 → 루프를 돌지 않고 그대로 보고
   ▼
⑤ Repair Planning ── 문제마다 전략 후보를 순서대로(이미 실패한 전략 제외)
   │
   ▼
   Checkpoint
⑥ Correction Execution ── Blender 연산(기록됨) 또는 UE Provider Job
   │
   ▼
⑦ Candidate Evaluation ── ② · ③ 을 **같은 조건으로** 다시 → before 와 비교
   │
   ├─ 개선됨 ─▶ 후보 채택(새 기준선) ─▶ 품질 기준 충족? ─ 예 ▶ 최종 검토(사람)
   │                                        └ 아니오 ▶ ④ 로
   └─ 개선 안 됨 ─▶ ⑧ Rollback ─▶ 다른 전략(⑤) ─ 한도 초과 ▶ NEEDS_REVIEW(최선 후보 보존)
```

### 1.2 역할 → 실제 수단

| 역할 | 수단 | 분류 |
| :--- | :--- | :--- |
| ① Scene Observation | Blender: `get_scene_state` · `get_object_details` · `mesh_report` · `rig_report` · `list_actions` / UE: `inspect_skeleton` · `search_animations` | Reuse |
| ② Numerical Validation | UE `validate_animation`(프로필 · 관통 · 손가락) + `motion_metrics.measure` / Blender `audit.py` / `fbx_inspect.py` / `rig_report` | Reuse |
| ③ Visual Review | Blender `capture_views` · `pose_test` / UE `capture_animation`(시트 · 연속 프레임). Claude 가 이미지를 직접 본다 | Reuse |
| ④ Error Diagnosis | Claude 의 판단 + 스킬의 **진단표**(증상 → 볼 지표 → 원인 후보). 출력은 정해진 모양의 문제 목록 | 스킬 문서 신규(Keyframe Coach 지식 Adapt) |
| ⑤ Repair Planning | 스킬의 **전략표**(문제 코드 → 전략 순서). 전략 하나 = 이름 있는 연산 묶음 또는 Provider | 스킬 문서 신규 |
| ⑥ Correction Execution | Blender MCP 연산(기록) / 기존 `fix.timing` · `fix.body` · `edits` Job | Reuse + Blender 편집 연산 Implement |
| ⑦ Candidate Evaluation | **평가 Tool 하나**: ② 를 돌리고 before 와의 차이 · 판정을 돌려준다 | Implement(얇음 — 기존 지표 호출 + 비교) |
| ⑧ Rollback / Retry / Fallback | 체크포인트 복원(Adapt) / 전략 바꿔 재시도 / 기존 실행기의 Provider 폴백(Reuse) | Adapt + Reuse |

Core 에 더하는 것은 **시도 기록** 하나다. Job 에 `repair_attempts[]{문제 코드, 전략, 체크포인트, 연산 기록, before/after 지표, 판정}` 를 남긴다. 세션이 끊겨도 어디까지 시도했는지 남고, 같은 전략을 되풀이하지 않는다.

### 1.3 '개선됐다'의 정의

- **목표 지표가 여유폭 이상 나아졌고**, **하드 게이트가 새로 깨지지 않았고**, **다른 추적 지표가 허용폭 넘게 나빠지지 않았다** — 셋 다여야 채택한다. 여유폭 · 허용폭은 PoC-0 기준선의 측정 잡음에서 정한다.
- 시각 검토는 같은 카메라 · 같은 프레임의 시트로 전후를 나란히 본다.
- 한도: 문제당 전략 3개, 루프 전체 시도 수 · 시간 상한(정책값). 넘으면 최선 후보를 남기고 멈춘다.

### 1.4 한계 (미리 적는다)

- **프레임 시트로 '타격감' · 완급을 판정하는 능력은 제한적이다** [추정]. 그래서 **초기 PoC 에서는** 루프의 채택 근거를 수치에 두고, 시각 검토는 보조 수단('눈에 띄는 파손이 없는가')으로 쓴다. 이것은 출발점의 안전한 기준이지 시각 평가의 최종 역할이 아니다(§1.5).
- "어색하다" 같은 열린 목표는 ④ 에서 근거 있는 문제로 바뀌어야 루프가 돈다. 초기 PoC 에서는 그 근거가 수치다. 바뀌지 않으면 손대지 않고 "수치상 문제를 찾지 못했다 + 본 것"을 보고한다. 근거 없이 고치기 시작하지 않는다.
- 이 한계가 실제로 어디까지인지가 PoC-4b 의 측정 대상이다.

### 1.5 시각 · 의미 평가의 단계적 확장 (향후 확장 요구사항 — 현재 PoC 를 늦추지 않는다)

수치가 모두 정상인 두 애니도 타격감 · 역동성은 다를 수 있다. 수치가 잡는 것과 잡지 못하는 것은 다르다.

| 정량 검증이 보는 것 | 의미 · 시각 검증이 보는 것 |
| :--- | :--- |
| 발 미끄러짐 | 공격 자세의 역동성 |
| 무기 파지 오차 | 공격 의도의 명확성 |
| 관절 회전 | 준비 동작의 설득력 |
| 루트 모션 | 움직임의 무게감 |
| 관통 | 팔로스루의 자연스러움 |
| 떨림 | 전체적인 타격감 |

| 단계 | 시각 · 의미 평가의 역할 | 필요한 것 |
| :--- | :--- | :--- |
| **초기 PoC** | 보조 수단. 채택 근거는 수치 | 지금 계획 그대로 |
| **MVP** | **시간 정보가 실린 프레임 열**(프레임 번호 · 시각 · phase 표시)과 **동작 구간 분석**을 평가 입력에 더한다 | `capture_animation` 연속 프레임 + phase 경계 주석, 구간별 길이 · 속도 곡선 요약 |
| **고도화** | 시각 · 의미 평가가 **수정 전략을 만든다**(예: "예비 동작이 짧아 무게감이 없다 → 예비 구간 리타임 + 골반 내림") | 의미 진단 → 전략 대응표, 의미 평가의 사람 판정 대비 일치율 측정 |
| **최종 승인** | 사용자가 실제 게임에서 재생해 판단 | — |

- 확장의 전제는 **의미 평가가 믿을 만한지를 재는 것**이다. PoC 마다 Claude 의 시각 소견과 사람 판정을 나란히 기록해 두면(§5.4) 그 일치율이 MVP · 고도화의 근거 자료가 된다. 그래서 초기 PoC 에서도 시각 소견은 채택에 쓰지 않더라도 **빠짐없이 남긴다.**
- 단계가 올라가도 하드 게이트(NaN · 관통 · 파손)는 의미 평가로 상쇄하지 않는다.

## 2. 신규 키프레임 애니메이션 제작

Keyframe Coach 를 가져와도 제작 능력이 생기지는 않는다(실체는 스킬 문서 + 감사 스크립트 [확인]). 제작에는 아래 연산이 Blender MCP 에 있어야 한다.

| 단계 | 하는 일 | 수단 | 분류 |
| :--- | :--- | :--- | :--- |
| Animation Planning | 동작 의도 → phase(예비 · 타격 · 팔로스루 · 복귀)별 프레임, 키 포즈 설명, 루트 이동, 무기 궤적 | Claude 가 Motion Spec(JSON) 작성. v0.1 의 phase · 제약 스키마 사용 | 스킬 + 스키마 |
| Key Pose Blocking | 키 프레임에 자세를 잡는다. 계단식 보간으로 먼저 검토 | `keyframe`(본 로컬 회전) · `pose_bones` — Reuse. **손 · 발 목표 위치로 자세 잡기**(`ik_pose`) — Implement. 운영 클립에서 자세를 가져와 출발점으로 쓰기(`pose_from` 방식) — Implement | Reuse + Implement |
| Keyframe Generation | 브레이크다운 · 중간 키, 보간을 곡선으로 | `keyframe` — Reuse | Reuse |
| F-Curve · 보간 | 핸들 · 이징, 키 이동, 구간 리타임 | `edit_fcurve` · `set_interpolation` · `retime_range` — Implement | Implement |
| IK / FK | 발 고정 · 양손 파지를 제약으로 걸고 풀기 | `create_ik_constraint` · `bake_action`(제약 결과 → 변형 본 키) — Implement | Implement |
| Polishing | 팔로스루 프레임 어긋내기, 손 · 무기 끝의 호(arc) 확인, 쿼터니언 뒤집힘 제거 | `audit.py` — Reuse. 궤적 추출(`trajectory`) — Implement | Reuse + Implement |
| 시각 검토 · 반복 | §1 의 루프 그대로 | — | — |

- **리그 전제:** UE 에서 내보낸 Vesper 스켈레톤에는 컨트롤 리그가 없다. 변형 본에 FK 로 키를 잡고, IK 는 임시 제약으로 걸었다가 베이크한다. Rigify 컨트롤 리그를 덧씌우는 방식은 PoC-4c 결과가 나쁠 때의 대안으로만 둔다.
- **기대 수준 [추정]:** 전신 공격을 처음부터 손으로 잡아 운영 품질이 나오리라고 보지 않는다. 블로킹 수준이 현실적인 첫 목표이고, 운영 클립의 자세를 출발점으로 쓰는 것이 품질을 올리는 가장 싼 방법이다. 어디까지 되는지를 PoC-4c 가 잰다.

## 3. 영상 기반 제작 — 네 경로

### 3.1 공통: 수치 분석과 의미 분석을 따로 만든다

| 산출물 | 만드는 주체 | 내용 |
| :--- | :--- | :--- |
| `motion_estimate` (NPZ) | 추출 모델(미정) | 관절 3D · 루트 · 접지 · **confidence** |
| `motion_semantics` (JSON) | Claude(프레임 시트 판독) | phase 경계 시각, 키 포즈 프레임, 공격 의도, 무기 · 손 제약, 불확실 구간 |

둘은 서로를 보지 않고 만든 뒤 합친다. **충돌은 숨기지 않고 표시한다** — 예: 의미 분석의 타격 프레임과 수치의 손 속도 정점이 N 프레임 넘게 어긋나면 그 구간을 '불확실'로 남긴다.

### 3.2 경로

| 경로 | 입력 | 쓰는 것 | 결과물 | 영상 품질에 대한 민감도 |
| :--- | :--- | :--- | :--- | :--- |
| **A 직접 복원** | 영상 | `motion_estimate` 전체 | 복원 모션 → 공통 포맷 → 리타깃 → 보정 | 높다(떨림 · 가림이 그대로 들어옴) |
| **B 키 포즈 재생성** | 영상 | `motion_estimate` 의 키 프레임 몇 개 + `motion_semantics` 의 타이밍 | Kimodo `key_pose` 제약 생성(기존 9-3 경로) | 중간 |
| **C 차이 분석 후 수정** | 영상 + **기존 애니** | 두 분석으로 '영상 대비 기존 애니가 어디가 다른가'(phase 길이 · 키 포즈 · 궤적) | **기존 애니를 고친 것** — 리타임 · 자세 오프셋 · 궤적 보정 | 낮다(전체 복원이 필요 없다) |
| **D 영상 생성** | 자연어 요구사항 | 영상 생성 → 적합성 검사 → A / B / C | 위 경로의 결과 | AI 영상의 신체 왜곡이 더해진다 |

- **C 는 독립 경로다.** A 가 실패해도(3D 복원이 거칠어도) 돈다 — 타이밍은 의미 분석과 2D 움직임만으로, 자세 차이는 키 프레임 몇 장으로 잡는다. 의미 분석만 쓰는 최소형은 추출 모델 없이도 가능하다.
- C 의 수정 실행은 기존 연산을 쓴다: `time_warp` · `offset_bone` · `bone_deltas`(UE) 또는 Blender 편집 연산.
- D 의 적합성 검사: 전신 · 고정 카메라 · 컷 없음(v0.1 프롬프트 규칙) + 프레임 간 신체 비율 · 무기 형태 일관성. 실패하면 재생성(유료라 시도 수 상한 · 승인).

### 3.3 원본 영상 ↔ 결과 렌더 비교 루프

```text
결과 애니 ─▶ 영상과 같은 시점 · 같은 phase 시각으로 렌더
          ─▶ 나란히 놓은 시트(의미 비교: Claude) + 수치 비교(phase 길이 오차 · 정점 시각 · 정규화한 2D 관절 차이 · 루트 궤적)
          ─▶ §1 의 루프(진단 → 수정 → 같은 조건 재비교)
```

단안 복원값은 정답이 아니다. 정답이 있는 시험(운영 애니를 렌더한 영상)에서만 '정확도'라는 말을 쓴다.

## 4. 메시 · 리그의 자율 개선

### 4.1 기능 범위

| 기능 | 필요성 | 수단 | 분류 |
| :--- | :--- | :--- | :--- |
| Tripo 메시 생성 · 내려받기 | 필수 | 얇은 Provider — 기존 Meshy Provider 구조(승인 · 장부 · 비동기) 재사용, 엔드포인트 · 가격표는 AutoRig `generators/tripo.py` 참고 | Implement(Reuse 구조) |
| 메시 구조 분석 | 필수 | `mesh_report` · `get_object_details` | Reuse |
| Topology 검사 | 필수 | `mesh_report` + `validate_blender.py` | Reuse / Adapt |
| 메시 직접 수정 | 필수 | Claude Blender Integration 의 modeling · topology Tool(`cleanup` · `mesh_edit` · `decimate` 등 — 이름만 확인, 본문 [미확인]) + Tripo GLB 결함(NaN · 원점 관절) 수선 | Reuse + Implement |
| 재질 · 텍스처 검사 | 필수 | `validate_blender.py`(UV · 재질 · 텍스처) + UE 임포트 뒤 확인 | Adapt |

| 스키닝 직접 수정 | 필수 | `bind_mesh` · `limit_weights` — Reuse. **영역 단위 가중치 수정**(본 영역 지정 → 대입 · 배율 · 스무딩 · 전이 · 정규화 · 좌우 대칭) — Implement | Reuse + Implement |

## 5. 검증 기준

### 5.1 파일 무결성과 의미적 동등성은 다른 검사다

| 검사 | 묻는 것 | 방법 | 쓰는 곳 |
| :--- | :--- | :--- | :--- |
| **파일 무결성** | 바이트가 같은가 | SHA-256 | 원본 불변 · 체크포인트 사본이 손상 없이 복원됐는가 · 산출물 manifest |
| **의미적 동등성** | 씬 · 애니 데이터가 같은가 | **씬 다이제스트** 비교(아래) | Headless Replay · 롤백 뒤 상태 · UE ↔ Blender 왕복 |

씬 다이제스트가 보는 것과 초기 허용 오차:

| 항목 | 비교 | 허용 오차(초안) |
| :--- | :--- | :--- |
| 아마추어 | 본 이름 · 부모 · 기준 포즈 행렬 | 위치 1e-4 m · 회전 0.01° |
| 포즈 · 애니 | 모든 프레임을 샘플한 본별 월드 변환 | 같음 |
| 메시 | 정점 수 · 면 인덱스(정확히) · 정점 위치 · UV · 재질 슬롯 | 위치 1e-4 m |
| 가중치 | 정점별 그룹 가중치 | 1e-4 |
| 액션 | 이름 · 프레임 범위 · fps · F-Curve 키 값 · 보간 종류 | 값 1e-5 |
| 메타데이터 | 커스텀 속성 · 단위 · 축 설정 | 정확히 |

**UE 로 돌아온 애니의 판정 (2026-11-27 사용자 결정 — PoC-2 결과 반영):**

| 단계 | 기준 | 묻는 것 |
| :--- | :--- | :--- |
| 임포트 뒤 **설정 복원** | 원본의 애셋 수준 설정(루트 모션 사용 · retarget source · 압축 설정)을 되돌린 뒤에 잰다 | FBX 에 실리지 않는 설정 때문에 생기는 차이를 빼기 위해. PoC 는 스크립트 최소 구현, 원본에서 자동으로 읽어 되돌리는 정식 단계(노티파이 · 커브 포함)는 MVP |
| **압축 전(raw)** | 위치 0.1 cm · 회전 0.1° | 왕복 · 수정 과정이 데이터를 망가뜨리지 않았는가 |
| **압축 뒤** | 원본과 같은 압축 설정에서, 원본 압축 ↔ 결과 압축의 차가 원본 자신의 압축 오차(PoC-2 측정: 위치 0.052 cm · 회전 0.068°)를 넘지 않는다 | 게임이 실제로 재생하는 값이 같은가. 설정을 되돌린 뒤의 실제 값은 PoC-4a 에서 처음 잰다 — 넘으면 수치와 함께 기준을 다시 정한다 |

**Headless Replay 의 성공 = 의미적 동등.** `.blend` 바이트 일치는 요구하지 않고 기록만 한다(다시 저장한 `.blend` 가 바이트까지 같으리라고 기대하지 않는다 [추정] — PoC-1 에서 잰다).

### 5.2 영상 기반 모션의 품질 — 다섯 축을 따로 보고한다

| 축 | 지표 |
| :--- | :--- |
| 정답 유사도 | 관절 위치 p95 · 회전 차 · phase 길이 오차 · 휘두름 정점 시각 · 루트 궤적 (정답이 있는 시험만) |
| 자연스러움 | 떨림 · 발 미끄러짐 · 바닥 · 몸 관통 · 튐 · 쿼터니언 뒤집힘 + 사람 판정(별도 기록) |
| 전투 적합성 | 예비 · 타격 · 복귀 길이가 운영 클립 범위 안인가 · 손 속도 정점 · 파지 유지 · 무기 끝 궤적 · 루트 이동 · 시작 · 끝 자세가 대기 자세와 이어지는가 |
| 제작 비용 | GPU 시간 · 금액 · 벽시계 시간 · 사람이 손댄 단계 수 |
| 수정 비용 | 게이트 통과까지의 루프 횟수 · 연산 수 · 남은 수작업 |

하나의 점수로 합치지 않는다.

### 5.4 PoC 는 판정이 아니라 증거를 남긴다

각 PoC 는 '통과 / 실패' 한 줄이 아니라 아래 묶음을 남긴다. 구현했다는 설명은 근거가 아니고, 이 묶음이 근거다.

| 남기는 것 | 내용 |
| :--- | :--- |
| 실제 결과물 | `.blend` · FBX · NPZ · UE 애셋 경로 — 파일마다 SHA-256 |
| 실행 로그 | Tool 호출 순서와 인자(연산 기록), Job 기록, Blender · UE 로그 발췌, 실패한 시도 포함 |
| 렌더 이미지 | 전 · 후 시트(같은 카메라 · 같은 프레임), 연속 프레임, pose test 렌더 |
| 측정값 | 지표 JSON(전 · 후 · 차이), 씬 다이제스트 비교 결과, 허용 오차 |
| 환경 | Blender · UE · 애드온 커밋 · 모델 커밋 · seed · 정책값 |
| 소견 | Claude 의 시각 소견과 사람 판정을 **칸을 나눠** 기록 — 사람 판정이 없으면 '없음'이라고 적는다 |
| 비용 | 벽시계 시간 · Tool 호출 수 · 루프 횟수 · 금액 |
| 한 장 보고 | 무엇을 했고, 무엇이 됐고, 무엇이 안 됐고, 무엇을 확인하지 못했는가 |

- 위치(안): `AssetPipeline/poc/<PoC>/<실행 ID>/` — Saved 밖(이 세션에서 Saved 는 열어 보일 수 없다)이고 Content 밖이다. 보고 · 지표 JSON · 작은 이미지는 추적하고, 큰 이진 파일은 추적하지 않고 해시만 manifest 에 남긴다.
- 실패한 실행도 같은 묶음을 남긴다. 실패를 지우거나 성공으로 고쳐 적지 않는다.
- 다시 돌릴 수 있어야 한다: 묶음 안의 입력 · 설정 · 연산 기록만으로 같은 실행을 재현한다.

| 확인 항목 | 판단 기준 | 검증 PoC | 근거로 남길 것 |
| :--- | :--- | :--- | :--- |
| Blender 제어 | 실제 메시 · 본 · 키프레임이 바뀌는가 | 1 (T2) · 4a | 수정 전후 씬 다이제스트 차이(바뀐 항목만) · 전후 캡처 |
| Rollback | 수정 전 상태로 정확히 돌아가는가 | 1 (T3) | 롤백 뒤 다이제스트 = 수정 전 · 체크포인트 파일 SHA-256 |

| 영상 기반 제작 | 레퍼런스와 비슷한 동작을 얻는가 | 3 · 3b · 3c · 5 | 다섯 축 표 · 영상 ↔ 결과 나란히 시트 |

'신규 애니메이션'과 'UE5 통합'의 마지막 판단은 사람이다. 자동 검사가 통과해도 사람 판정이 없으면 '자동 검사 통과 · 사람 판정 대기'로 적는다.

## 6. GPL · AGPL 코드의 활용

법률 자문이 아니다. 라이선스 원문과 Blender 재단 안내는 채택 전에 다시 읽는다(오늘 blender.org 라이선스 페이지는 봇 확인 화면에 막혀 읽지 못했다 [미확인]). 아래는 배포 방식별로 무엇이 걸리는지의 정리다.

| 쓰는 방식 | 걸리는 의무 [추정 — 원문 재확인] | 판단 |
| :--- | :--- | :--- |
| 내 PC 에서 도구로 실행만(배포 없음) | GPL · AGPL 의 의무는 배포(전달) 때 생긴다. AGPL 은 여기에 '수정본을 네트워크로 남에게 서비스할 때'가 더해진다 | 가능 |
| **우리 저장소에 코드를 넣어 공개** | 그 코드와 파생물은 같은 라이선스(GPL/AGPL)로 소스 공개. 저장소의 나머지와 '한 프로그램'으로 볼 여지가 생긴다 | **하지 않는다** |
| 저장소 밖에 따로 설치하고 별도 프로세스(CLI · 파일)로 호출 | 우리는 그 코드를 배포하지 않는다. 별도 프로그램으로 보는 것이 일반적이나 결합 정도에 따라 판단이 갈릴 수 있다 | AutoRig 를 폴백 리거로 쓸 때의 유일한 방식 — PoC-6 뒤 결정 |
| 포크해서 고친 뒤 **그 포크를** GPL 로 공개 | 의무 충족 | 필요해지면 가능 |
| 코드를 읽고 방식 · 수치만 참고해 새로 작성 | 아이디어 · 알고리즘 · 수치는 저작권 대상이 아니다. 코드 구조를 옮겨 적지 않고 출처를 적는다 | AssetForge · AutoRig · HY-Motion-Pipeline 에 적용 |
| 도구가 만든 **산출물**(FBX · 애니)을 게임에 넣기 | 프로그램의 출력은 보통 그 프로그램 라이선스에 묶이지 않는다. 대신 서비스 · 모델 약관(Tripo · Viggle · Kimodo)이 정한다 | 서비스 약관이 관건 |
| Blender 안에서 `bpy` 를 쓰는 우리 스크립트를 공개 | Blender 재단은 Blender API 를 쓰는 스크립트 · 애드온의 배포에 GPL 호환 라이선스를 요구하는 것으로 알려져 있다. MIT 는 GPL 호환 | Blender 쪽 코드는 한 폴더에 모으고 GPL 호환 라이선스로. Core 와는 소켓 · CLI 로만 통신 |

**결론(안):** MIT 셋만 코드를 가져온다. GPL · AGPL 은 지금 단계에서 코드를 가져오지 않고 참고만 한다. AutoRig 의 외부 도구 사용은 PoC-6 에서 폴백 리거가 실제로 필요하다고 나오면 그때 원문을 읽고 정한다. 이 저장소가 공개인지 비공개인지에 따라 '공개' 행의 무게가 달라진다 — 확인 필요.

## 11-3. PoC-2 결과가 계획에 주는 영향 (2026-11-27, 증거 `AssetPipeline/poc/poc2/R20261127_0029/`)

총괄 세션이 다시 확인한 것: 보고서 ↔ `combos/C00_base/row.json`(위치 최대 0.00069 cm · 회전 최대 0.00177° · 키 · fps 같음) 대조, 왕복 FBX `C00_base.fbx` 의 SHA-256 재계산(manifest 와 같음), 정답 `.uasset` SHA-256(PoC-0 때와 같음), 작업 트리(변경은 `AssetPipeline/` 뿐), UE ↔ Blender 나란히 시트 열람. 시험을 다시 돌리지는 않았다. 사람 판정은 없다.

| 발견 | 계획에 주는 영향 |
| :--- | :--- |
| 무편집 왕복 오차 0.0007 cm · 0.0018°(기준 0.1 cm · 0.1°), 길이 · fps · 키 수 · 루트 이동 보존 | **Blender 에서 고친 결과를 UE 로 가져오는 길의 전제가 성립한다.** PoC-4a 의 Blender ↔ UE 비교에서 왕복 자체의 차이는 무시한다 |
| C++ · 빌드 없이 에디터 Python(`AssetExportTask`)으로 내보냈다 | PoC 에는 충분. 정식 구현 때 Tool 로 옮길지는 뒤에 정한다(에디터 안 임의 코드 실행 경로라 그대로 쓰지 않는다) |
| UE 의 `root` 본이 Blender 에서는 **아마추어 오브젝트**가 된다(본 171개). 이름을 바꾸면 루트 이동이 사라지거나 스켈레톤이 쪼개진다 | Blender 쪽 연산 · 지표 · 다이제스트는 루트를 오브젝트 변환으로 다룬다. 아마추어 이름은 Core 가 고정한다 |

| **애셋 수준 설정이 FBX 에 실리지 않는다** — 루트 모션 사용 · retarget source · 압축 설정(노티파이 · 커브도 같은 이유로 사라질 것 — 이 클립엔 없어 미측정) | 임포트 뒤 **설정 복원 단계**가 필요하다(원본에서 읽어 되돌린다). FR-13 의 노티파이 저작과 같은 자리 |

| `capture_animation` 은 루트 모션 설정에 따라 구도가 달라진다(PoC-0 의 빈틈이 실제 문제로 나타남) | 카메라 고정 인자(C++ 소규모 · 빌드 2회)가 여전히 필요하다 — PoC-4 준비 때 정한다 |
| 다이제스트: UV · 재질 슬롯 · 가중치 · F-Curve 는 Vesper 데이터로 동작. 고칠 것 셋(액션 이름 대응 · 엣지 순서 · 허용 오차 단위). 베지어 보간 키는 여전히 미검증 | 다이제스트 Adapt 목록에 추가. 베지어는 PoC-4c(신규 키프레임)에서 처음 실제 데이터가 생긴다 |
| MCP 는 이번에도 Claude 세션의 Tool 로 붙지 않았다(스크립트 호출) | 대화형 제어는 아직 0회 — PoC-4 에서 처음 잰다 |

**PoC-4 의 세션 나눔(총괄 판단).** 4b(자율 수정)는 '어떤 결함을 넣었는지 모르는' 시험이라, 결함을 넣는 세션과 고치는 세션이 같으면 성립하지 않는다. 그래서 ① 준비 + 4a(지정 수정 · Blender ↔ UE 비교 · 결함 주입기와 봉인된 정답지) → ② 4b(새 세션 — 정답지를 보지 않는다) → ③ 4c(신규 키프레임) 순으로 연다.
