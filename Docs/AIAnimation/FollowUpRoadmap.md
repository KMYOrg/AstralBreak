- 근거 수치는 지침서의 절 · 부록 B 행에서 가져왔다. 같은 값을 이 문서에서 다시 재지 않았다.

## 3. U1 — 생성 선별 · 기준 보정

**목적:** 8-1 선별 점수를 지금의 파이프라인(생성 → 8-3 시간 · 다리 보정 → 8-4 대상 쪽 보정)에 맞게 다시 정한다. 뒤 단계가 고칠 수 있는 결함보다 **못 고치는 결함**으로 후보를 가르게 하고, 남아 있는 8-1 사람 판정을 마감한다.

**지금 (근거):**
- 선별 = `selection.py` — 가중치 grip 3 · stance 2 · swing 2 · attack 2 · clearance 1 · breakage 1 · cross 2 · head 2, 기준값 발 좌우 비 2.5 · 폭 5.0 · 궤적 폭 하한 1.0 · 경고 벌점 0.5 · 팔 꼬임 20 · 50% · 머리 근접 5 · 25%(머리 본 한 점 10 cm × scale 안).
- 설계 시점(2026-10-26)에는 8-3 · 8-4 가 없었다. 지금은 뒤 단계가 고친다:
  - 넓은 다리 → 8-3 `stance_width` · 느린 휘두름 → 8-3 `fix.timing`(가속 · 트림) · 팔-몸 관통 · 짧은 머리 관통 → 8-4 `fix.body`.

## 4. U2 — 세그먼트 생성 · 연결

**목적:** 여러 단계 동작(준비 → 베기 → 복귀, 대시 → 도약 → 공중 회전 → 공격 → 착지 → 복귀)을 세그먼트로 나눠 만들고 잇는다. 한 프롬프트로 만들 때의 문제 — 동작 구간 비율이 낮고 정지 꼬리가 길다(8-1 소견 ④ '흐느적' · 4초 중 정지 꼬리 2.2 ~ 2.5초) — 를 줄이고, 게임에 필요한 구간(몽타주 섹션 · 타격 창)을 함께 낸다.

**지금 (근거):**
- 지침서 §11 은 원칙만 있다(세그먼트마다 길이 · 시작 · 끝 포즈 · 루트 모션 · 접촉 · 무기 · 타이밍 제약, 세그먼트별 Provider, 연결부 연속성은 수치 검증). 구현은 없고, 라우터는 근사 Provider 일 때 한계 `SEGMENTED_PLAN_SUGGESTED` 만 단다(`router.py`).
- 요청 `prompt` 는 문자열 하나(`request.py`) — Kimodo 호출도 프롬프트 하나를 목록으로 감싸 `multi_prompt=True` 로 넘긴다(`local_ai/kimodo_run.py` `generate`).
- **Kimodo 다중 프롬프트(소스 `kimodo/model/kimodo_model.py` `_multiprompt` · CLI 문서 확인):** 프롬프트마다 길이를 주면 순서대로 생성한다. 다음 세그먼트의 처음 N 프레임(`num_transition_frames`, 기본 5 = 0.17초)에 앞 세그먼트 끝의 전신 · 손발 제약(FullBody + EndEffector)을 걸고, 겹친 N 프레임을 선형 블렌드한다. 전역 제약 목록은 세그먼트마다 시간으로 잘라(`crop_move`) 쓰므로 우리 제약(`root_path` · `keep_pose` · 파지 2차 end-effector)이 이은 타임라인 전체에 그대로 걸린다.

## 5. U3 — 키 포즈 제약 · 역리타깃

**목적:** Vesper(대상) 쪽 자세 — 운영 애니의 타격 자세 · 대상 쪽에서 고친 자세 · 무기 부착에 맞는 손 방향 — 를 Kimodo 생성의 **키 포즈 제약**으로 되돌려, 사이 동작은 모델이 채우게 한다. 대상 쪽 보정(8-4)이 '고치기'라면 이쪽은 '동작 자체를 바꾸는' 경로다. 8-4 에서 대상 쪽으로는 풀 수 없다고 판정한 것들의 뿌리 해결이다.

**지금 (근거):**
- **Kimodo 쪽은 준비돼 있다** — 제약 `fullbody`(관절 로컬 회전 axis-angle + 엉덩 위치 → FK 관절 위치를 조건으로) · 손 · 발 end-effector(위치 + 회전) · `root2d`(소스 문서 `docs/user_guide/constraints.md`). 우리 요청은 `keep_pose{npz, times, part}`(이전 **Kimodo 결과 NPZ** 의 자세 고정)와 `kimodo_raw{path}`(Kimodo 제약 JSON 그대로)를 이미 받는다(`local_ai/constraints.py` · `kimodo_run.build_constraints`).

**목적:** 생성 → Blender 다리 보정(`fix.ops`) → 리타깃 → 시간 보정(`fix.timing`) → 대상 쪽 보정(`fix.body`)으로 이어지는 합본 Job 에서 다리가 단계 사이에 다시 망가지는 곳을 막고, 다리 블록이 아직 받지 않는 요청(다리 샘플 · 발 회전 · 땅 간섭)을 넣는다. 8-3 의 시간 · 다리 기준값도 여기서 다시 본다.

**지금 (근거):**
- **시간 보정 뒤 발 미끄러짐** — 합본의 Vesper 접지 미끄러짐 p95 3.7 ~ 9.8 cm/s. 8-3 다리 보정(리타깃 전 · 대상 다리 모델)이 고정한 발을 시간 보정의 `time_warp antialias`(1배보다 빠른 곳을 σ = antialias · √(배율² − 1) 프레임 가우시안으로 거름)가 다시 거른다. `fix.body` 의 다리 블록은 접지 프레임을 '원래 키'(시간 보정 뒤)로 pin 하므로 미끄러짐이 그대로 남는다(부록 B '시간 보정의 발 미끄러짐'). `fix.body.legs.pins` 는 지금 `auto` 하나뿐이다.
- **공중 경로의 근사** — 8-4d 공중 경로는 무릎 · 발목 위치 저크 최소 + 충실도의 위치 최적이다. 발이 지나는 길이 2.8 ~ 4.1 cm 바뀌고, 땅 · 다른 다리와의 간섭은 보지 않는다(관통 지도는 팔 점만 — 다리끼리 `clearance.legs` 는 측정 옵트인). 발 회전은 원래 컴포넌트 회전 그대로, 접지 경계가 없는 클립(접지 0%)은 건너뛴다(`LEG_PATH_SKIPPED` · `NO_CONTACT`)(부록 B '다리 공중 경로의 근사').
- **다리 블록이 받지 않는 요청** — `pose_from` 의 legs · 골반 프리셋과 발 회전 목표는 `NOT_SUPPORTED`(발 pin 과 부딪히는 규칙이 없다 — 부록 B '샘플 전이 범위 밖').
- **`swing_path` auto 의 범위** — auto 는 같은 Job 의 `fix.ops` 다리 op 가 있을 때만 켠다. 이미 다리를 고친 기존 애셋은 `on` 을 줘야 하고, 원본 생성물 자체의 발 튐(칼 시험 3.42)도 `on` 이면 1.41 로 줄지만 기본은 아니다(부록 B '`swing_path` auto 의 범위').
- **발끝 접지** — 8-3 다리 보정은 발목만 고정한다(뒤꿈치를 든 발끝 접지는 고정하지 않음 — 부록 B '다리 보정의 대상 모델').
- **8-3 기준값** — 사용자 판정은 통과했지만 남은 보정 후보: 가속 상한(검은 × 2.0 에서도 운영 최저에 못 미침 — 생성 정점 321 ~ 637 vs 운영 1,200 ~ 2,600 cm/s) · 복귀 배율 1.5 · 발 간격 상한 3.0 · 머리 · 꼬리 남김 0.2 · 0.3초(antialias 1.0 은 확정)(부록 B 'Phase 8-3 결과의 사람 판정 · 기준값').

**범위:**
- **U6-a 시간 보정 뒤 발 고정** — 두 길:
  - (가) `fix.body.legs.pins: hold` — 접지 구간마다 발목(과 발볼)을 그 구간의 대표 위치(구간 평균 또는 첫 접지 프레임)에 고정하고 다리 IK 로 맞춘다. 다리 블록 안이라 공중 경로 · 소프트 무릎과 한 풀이. Python 만. **추천.** 합본처럼 시간 보정이 있는 Job 에서 auto 로 켤지 정한다(`swing_path` 와 같은 꼴).
  - (나) C++ `time_warp` 에 접지 구간의 발 본을 거르지 않는 옵션 — 골반 · 루트는 걸러지는데 발만 안 거르면 다리 길이가 어긋날 수 있어 (가)보다 위험.
- **U6-b 공중 경로 간섭** — 다리 블록 잔차에 바닥 높이(발목 · 발볼 ≥ 바닥 + 여유)와 다리끼리 거리(8-4a `clearance.legs` 지도 재사용)를 넣는다. 발 회전도 공중 구간에서 발목 경로에 맞춰 부드럽게(선택).
- **U6-c 다리 샘플 · 발 회전 목표** — 규칙: 접지 프레임은 발 pin 이 이기고 샘플 다리는 골반 상대로 덮은 뒤 IK 로 pin 에 되돌린다 · 공중 프레임은 샘플 그대로(완급) · 발 회전 목표는 컴포넌트 회전 오버라이드 + 완급, 접지 중이면 접지점(뒤꿈치 · 발볼) 둘레로 돌린다. 큰 다리 동작 변경은 생성 쪽(U3).
- **U6-d 발끝 접지** — 접지 판정을 발목 · 발볼 둘로 나눠 뒤꿈치를 든 프레임은 발볼을 고정한다(8-3 Blender 보정 · 8-4 다리 블록 둘 다 해당 — 대상 쪽만 할지 정한다).
- **U6-e 8-3 기준값 재검토** — 가속 상한 · 복귀 배율 · 발 간격 상한 · 남김 시간을 생성 · 운영 분포 표로 다시 정한다(U1 의 선별 재정의와 같이 보면 좋다 — 느린 휘두름을 선별이 거르는지 시간 보정이 살리는지). **→ 9-1 결과: 바꾸지 않음**(사용자 결정 2026-11-01 — 분포 표는 지침서 §14 '9-1', 느린 휘두름은 시간 보정이 살리고 남는 차는 9-2).

**범위 밖:** 다른 RTG 구성의 다리 모델(U7-c) · 큰 다리 동작 변경(U3) · 달리기처럼 접지 판정이 비는 클립의 공중 경로(접지 판정 자체 — 필요하면 U6-d 와 함께).

**선행:** 없음. U6-e 는 U1 과 함께 보는 게 좋다.

**결정 필요:** ① U6-a (가) / (나) · `pins: hold` 를 시간 보정 Job 에서 auto 로 켤지 ② 바닥 높이를 어디서 얻을지(기준 포즈 발 높이 vs 첫 접지 프레임) ③ 발 회전 목표의 접지 중 회전 중심 ④ 발끝 접지를 대상 쪽만 할지 Blender 보정까지 할지 ⑤ 8-3 기준값을 바꿀지(기존 판정 통과 결과가 바뀐다).

**완료 기준:**
1. 합본 2건(낫 정정 · 검 선택)의 접지 미끄러짐 p95 3.7 ~ 9.8 → 다리 보정본 수준(≤ 1 cm/s) · 무릎 떨림 · 공중 경로 수치가 8-4d 보다 나빠지지 않음.

## 10. U8 — 다양한 스켈레톤

**목적:** Vesper 하나로 검증한 파이프라인(리타깃 · 생성 선별 · 8-3 · 8-4 보정 · 캡처)을 다른 대상 캐릭터에서도 그대로 쓰게 한다. 3D 메시 생성(U10)이 만든 캐릭터를 대상으로 삼는 경로의 바탕이기도 하다.

**지금 (근거):**
- **코드는 대부분 역할 · 치수 기반이다** — `fix.body` 의 본은 `inspect_skeleton template_match` 역할(골반 · 팔 · 다리 · 머리), 손가락은 `suggest_finger_chains`, 몸 지도는 대상 메시 LOD0(C++), 기준 크기 `scale` = 펠비스 높이 / 100, 접지 판정 = 다리 길이 비, 파지 띠 = 대상 메시 골격 치수. 메시 · 스켈레톤 이름이 박힌 곳은 C++ · 설정 · Python 코드에 없다(주석 · 예시 문구만 — grep 확인).
- **그러나 기준값은 Vesper 운영 애니에서 정했다** — 시간 보정 목표 정점 1,200 cm/s(운영 Vesper 낫 정점 최저, `timing.py`) · 다리 보정 끝 자세 발 좌우 비 2.1 · 대기 1.9(`fix_ops.py`) · 팔 교차 · 머리 근접 기준(운영 낫 4개, `motion_metrics.py`) · 선별 발 좌우 비 2.5(Vesper 엉덩 폭 ≈ 18 cm, `selection.py`) · 낫 손 간격 55 ~ 65 cm(`request.py`). 다른 캐릭터는 스타일 · 무기 · 체형이 다르다.
- **검증된 대상은 Vesper 하나** — 8-1 ~ 8-4 통합 · 사람 판정 모두. Phase 1 · 2 는 여러 소스 계열(UE4 마네킹 · UE5 Manny · Narmaya · SB)을 Vesper 로 옮겨 봤을 뿐 대상으로 쓴 적은 없다.
- 비표준 스켈레톤(Narmaya · SB)은 자동 캐릭터라이즈가 전부 실패했고(감사 §2) SOMA 처럼 수동 체인이 필요하다. 정면 축이 다른 것(SB +X)은 `facing_yaw_deg` 로 맞춘다(부록 B '얼굴 방향이 다른 스켈레톤'). 8-3 다리 보정은 대상 메시 치수 기준이라 대상이 바뀌면 다시 보정한다(부록 B '다리 보정의 대상 모델').
- **프로젝트 안 후보** — IdaFaber 남성 `SK_STREETDEMON_M_BODY_FULL`(Vesper 와 같은 계열 · 다른 체형) · UE5 Manny `SKM_Manny_*`(표준) · Greystone(Paragon — 큰 체형 · 갑옷) · Narmaya `pl1400`(비표준) · SB `CH_P_EVE_01_Body`(비표준 · +X 정면). 분리 메시(`Separated`)는 몸 지도가 메시 하나라 FULL 메시를 쓴다.

**범위:**
- **U8-a 대상 일반화 점검** — 표준 계열 2개(IdaFaber 남성 · UE5 Manny)에 같은 요청(낫 정정 · 검 선택 합본 = 생성 → 8-3 → 8-4, 그리고 기존 Vesper 애니 하나를 그 대상으로 리타깃한 뒤 `fix.body`)을 돌려 실패 · 한계를 표로 만든다. 예상: 역할 · 치수 기반이라 그대로 돌고 기준값 차이만 드러난다.
- **U8-b 대상별 기준값 프로필** — Vesper 운영 애니에서 정한 기준(정점 · 발 좌우 비 · 교차 · 머리 · 손 간격)을 대상 · 스타일 프로필로 분리한다(정책 또는 요청 `target_profile`). 프로필이 없으면 Vesper 값 + 위험 표시.

- **U8-d** (U7-c 와 함께) 다른 리타기터 구성에서 다리 모델 예측 = 실측.
- U10 이 메시를 만들면 그 캐릭터가 U8-a 의 다음 대상이다.

**범위 밖:** 사족 · 비인간형(Kimodo SOMA 는 사람 골격) · 대상 메시 제작(U10) · 세그먼트마다 대상이 다른 경우.

**선행:** 없음(U7-c 는 함께). U10 은 U8-a 뒤.

**결정 필요:** ① 대상 후보(표준 2 + 비표준 1 추천) ② 기준값 프로필의 자리(정책 vs 요청) ③ 다른 캐릭터의 무기 부착 데이터(소켓 · DA)를 시험용으로 만들지 — 운영 애셋 변경은 별도 승인.

**완료 기준:**

**무게:** 중간 — Python(프로필 · 계획 검사)에 에디터 실측이 많다(대상마다 IK Rig · 무기 · 캡처). C++ 는 비표준 대상에서 문제가 나올 때만.

## 11. U9 — 영상 포즈 추정 타당성 조사

**목적:** 참조 영상(사람이 찍은 동작)에서 동작을 얻는 경로가 이 파이프라인에 들어올 수 있는지 **조사만** 한다 — 모델 · 서비스의 라이선스 · 데이터 정책 · 출력 형식 · 품질을 확인하고, Provider 로 넣을지 · 키 포즈 원천(U3)으로만 쓸지 · 접을지를 정한다. 파이프라인 코드는 바꾸지 않는다.

**지금 (근거):**
- Phase 5 로컬 모델 조사([로컬 모델 조사](LocalModelSurvey.md))의 판정 기준(§1 — 코드 · 가중치 · 학습 데이터 라이선스 · 출력 · 실행 환경)과 결론을 그대로 쓸 수 있다. 핵심: **SMPL 바디 모델 · AMASS 는 비상업 연구 · 교육 · 예술만 허용하고 상업 목적의 신경망 학습 · 이용을 금지**한다(§2). HumanML3D 계열 Text-to-Motion 이 전부 '상업 부적법'이 된 이유이고, 개인 포트폴리오가 허용 범위에 드는지는 원문이 정하지 않아 사용자 판단이었다(§4).
- 단안 영상 3D 자세 복원 모델은 대개 SMPL · SMPL-X 골격을 출력하고 SMPL 계열 데이터로 학습한다 — 같은 제약에 걸릴 가능성이 높다(미확인 — 조사 대상). 기록: HY-Motion 은 영상 1,200만 클립을 GVHMR 로 복원해 학습 데이터로 썼다(§3.2).
- 들어올 자리는 이미 있다:
  - 파일 입력 — 요청 `motion_file{path, unit, facing, range, axis_forward, axis_up}`(Phase 4 — Blender 변환 단계가 읽는다, 단위 · 축 · 정면 지정) → `import_animation_file`(리샘플 · 경계 스냅) → 리타깃(Phase 1, 정면 맞춤 `facing_yaw_deg` · 소스 체인 — SMPL 골격이면 SOMA 처럼 수동 체인) → 8-3 · 8-4 보정 → 캡처.
  - 외부 서비스 — Phase 6 `external.meshy` 의 공통 구조(승인 · 장부 · 요청 로그 · 비동기 Job · 키는 환경 변수만).
  - 로컬 모델 — Phase 5 `local_ai` 의 전용 venv 서브프로세스 구조.
  - 키 포즈 — U3 `key_pose`: 영상 자세를 몇 프레임만 키로 주고 사이는 Kimodo 가 채우면 영상 복원의 떨림 · 발 미끄러짐 · 가림에 덜 민감하다.

**범위 (조사):**
1. **후보 표** — (a) 로컬 오픈 모델(예: 조사 시작점 GVHMR · WHAM · 4D-Humans 계열 — 이름만, 라이선스 미확인) · (b) 상용 서비스(예: Move.ai · DeepMotion · Rokoko Video · Plask — 가격 · 약관 미확인). 항목 = 코드 · 가중치 · 학습 데이터 라이선스, 출력 골격 · 형식(BVH · FBX · SMPL 파라미터), 세계 좌표 루트 궤적 · 발 접지 복원, 손 · 손가락, 단일 카메라 · 가림 조건, 실행 환경(로컬 GPU), 서비스는 가격 · API 유무 · **업로드 영상의 학습 사용 여부(데이터 정책)** · 결과 보관.
2. **판정** — Phase 5 조사와 같은 형식(원문 인용 · 출처)으로 상업 적법 · 포트폴리오(사용자 판단) · 호환을 가른다.
3. **오프라인 시험 1 ~ 2 영상** — 적법 · 호환 후보만, 사용자가 권리를 가진 영상(직접 찍은 것). 결과를 지금 파이프로 Vesper 에 리타깃해 8-1 지표(떨림 · 발 미끄러짐 · 손목 꺾임 · 루트 궤적)와 캡처로 본다. 파이프라인 코드 변경 없음(파일 입력 경로).
4. **권고** — 채택(Provider 설계 초안 — Phase 6 형식) · 키 포즈 원천으로만(U3 와 함께) · 미채택 중 하나.

**범위 밖:** Provider 구현 · 영상 촬영 · 편집 도구 · 얼굴 · 손가락 정밀 캡처.

**선행:** 없음. 키 포즈로 쓰는 결론이면 U3 뒤에 붙는다.

**결정 필요:** ① 범위 — 로컬 모델만 / 상용 서비스 포함 ② 시험 영상 원천(사용자 촬영 권장 — 권리) ③ 모델 내려받기 · 설치 · 서비스 가입(사용자 승인 — 유료 서비스는 Phase 6 처럼 승인 뒤).

## 12. U10 — 3D 메시 생성(Tripo) 채택 여부

**목적:** 애니 파이프라인 밖의 별도 트랙 — 텍스트 · 이미지 → 3D 메시 + 자동 리깅 → UE 캐릭터로 가져와 Vesper 애니를 리타깃하는 경로 — 를 열지 닫을지 정한다. 착수는 '애니 자동화 뒤'(사용자 결정 2026-10-25, 지침서 §14 '별도 트랙'). 이 문서는 결정에 필요한 것만 정리한다.

**지금 (근거):**
- **기존 Tripo 조사(공유 노트 `phase6-tripo-survey-design.md`, 2026-10-25)는 Tripo 를 '모션' Provider 로 봤고 그 권장이 '채택 안 함'이다** — 텍스트 → 모션이 없고 리깅한 메시에 고정 프리셋(v3 이족 11개 · v1 101개)을 입혀 줄 뿐이라, 이미 있는 애셋(CombatMasterAnimBundle · Vesper `AS_`)과 겹치고 빈칸(사교 감정 표현)은 Mixamo 수동 다운로드가 비용 0 대안이다. **메시 생성 트랙 자체는 결정되지 않았다.**
- 그 조사의 메시 쪽 사실(글로벌 v3 — `openapi.tripo3d.ai/v3`): text-to-3D 10 ~ 20 크레딧 · 10 ~ 120초, Auto Rig 25 크레딧(`v3.0-20260909` 인간형 · `spec: unreal` = UE 마네킹 명명), 1 크레딧 = $0.01 · 최소 충전 $1, 무료 API 크레딧 양은 공식 문서로 확정 불가(키를 만든 뒤 잔액 조회), 결과 URL 5분 만료, V2 는 2026-11-01 퇴역 → v3 만. **약관 §5.2.1: 무료 사용자의 출력은 Tripo 소유** · §5.2.2: 유료 사용자는 입력 · 출력을 소유하고 학습에 쓰이지 않는다. 출력 FBX 리그의 본 이름 · 기준 포즈 · 단위 · 축은 문서에 없다 → 첫 실제 1건에서 실측.
- **우리 쪽 빈칸** — 지금 임포트(`import_animation_file`)는 리타깃 소스용이라 재질 · 텍스처를 끈다 → 메시 · 재질 · 텍스처를 가져오는 경로가 새로 필요하다(지침서 §14 '별도 트랙'). 그 뒤는 있는 도구다: IK Rig(`create_ik_rig` — UE 명명이면 자동 캐릭터라이즈 가능성) · 리타깃 · 몸 지도(대상 메시 LOD0 — C++) · 캡처.
- 재사용: Phase 6 외부 API 공통 구조(승인 · 장부 `(plan_id, attempt)` · 요청 로그 · 비동기 Job · 키는 환경 변수만 · 기본 URL 고정).
- 애니 쪽과 만나는 곳: 생성 · 리깅한 캐릭터가 U8 의 새 대상이 된다.

**범위:**
- **U10-a 결정 자료** — 무료 크레딧 양(키 생성 뒤 잔액 조회 — 사용자) · 유료일 때 1 캐릭터 비용(생성 10 ~ 20 + 리그 25 ≈ $0.35 ~ 0.45 + 재시도) · 출력 소유권(포트폴리오 · 게임에 쓰려면 유료) · 대안(다른 메시 생성 서비스 · 로컬 모델 — 판정 형식은 Phase 5 조사 · U9 와 같게, 또는 마켓 애셋으로 충분하면 닫는다).
- **U10-b (채택 시) 메시 임포트 경로** — 스켈레탈 메시 · 재질 · 텍스처를 가져오는 Tool(새 C++ Tool 또는 `import_animation_file` 옵트인)과 결과 검증(본 수 · 기준 포즈 · 스킨 가중 · 정면).
- **U10-c (채택 시) 메시 Provider** — Phase 6 구조로 텍스트 · 이미지 → 메시 → 리그 → 임포트, 계획 = 비용 · 승인 · 장부.
- **U10-d (채택 시) U8 대상으로** — 리타깃 · 합본 보정 · 캡처 사람 판정.

**범위 밖:** 게임 캐릭터 블루프린트 통합 · LOD · 물리 · 천 · 얼굴 리그 · 마켓 메시를 외부 서비스로 올리기(입력에 권리를 주장하는 서비스 — 기존 조사 M2 거부와 같은 이유).

**선행:** U0(애니 자동화 마감). U10-d 는 U8-a 뒤.

**결정 필요:** ① 트랙을 열지, '검토 · 미채택'으로 기록만 하고 닫을지 ② 연다면 유료 사용(출력 소유권) ③ 입력 — 텍스트 vs 이미지(이미지는 권리 확인) ④ 후보 — Tripo 만 vs 대안 조사 포함.

**완료 기준:**
- 연다면: 캐릭터 1개 생성 → 임포트(재질 포함) → IK Rig → Vesper 애니 리타깃 · 합본 보정 → 캡처 · 비용 장부 · 원본 불변 · 사람 판정.
- 닫는다면: 지침서 §14 '별도 트랙'과 §2.4 에 '검토 · 미채택'과 근거를 기록.

**무게:** 결정. 열면 무거움 — C++ 메시 임포트 + 외부 Provider + U8 연계.
