# 1부. 게임 기획 확정 컨텍스트

> **정정 (2026-11-11):** 제목의 '확정' 은 원문 표기다. 표식처럼 기획에 속하는 요소는 수시로 바뀌거나 없어질 수 있다. 구현 설계는 특정 기획 해석에 묶이지 않게 한다 — 값은 데이터에 두고, 원문 안에서 읽기가 갈리는 개념은 설계 문서가 한쪽으로 정하지 않는다.

## 0. 프로젝트 목적

이 프로젝트는 UE5 클라이언트 프로그래머 취업/포트폴리오/역량 강화용으로 설계 중이다.
목표는 게임 전체 완성이 아니라 플레이 가능한 한 판 버티컬 슬라이스를 만드는 것이다.
사용자는 이미 Listen Server 기반 UE5 프로젝트, GAS, 복제/예측, InitState, 멀티플레이 구조 설계 경험이 있다.
그래서 이번 프로젝트는 그 강점을 살리되, 협동 PvE 레이드 / 보스전 / 빌드 / 준비 시스템까지 보여주는 방향으로 잡고 있다.

> **정정 (2026-11-11):** 프로젝트 목적에 **AI 활용 능력 증명**이 더해졌고, 요즘은 이것이 주목적이다. 게임 컨셉은 **그랑블루 판타지 리링크**를 참고하면 쉽게 이해된다(컨셉 이해용 참고작).

## 1. 장르 / 프로젝트 한 줄 정의

장르는 다음으로 확정했다.

**PvE / 3인칭 액션 / 멀티플레이 협동 / 스테이지 클리어형 게임**

프로젝트 한 줄 정의는 다음으로 확정했다.

**4인 협동으로 스테이지를 돌파하며 보스의 브레이크와 팀 체인 버스트를 활용해 화력을 집중하는 3인칭 PvE 액션 레이드**

## 2. 코어 전투 판타지

코어 전투 판타지는 다음 방향으로 확정했다.

플레이어는 일반 공격과 회피·가드·패링·원거리 전환을 통해 전투 기여와 오의 게이지를 축적하고, 보스의 상태 사이클(Mode → OverDrive → Burst Aura → Break)에 대응하며 유리한 타이밍에 오의와 체인 버스트를 연계해 합동 화력을 집중한다.

핵심 감정선은 다음이다.

* 패턴을 버틴다
* 기회를 만든다
* 다 같이 터뜨린다

즉, **대응 → 국면 전환 → 집중 화력** 구조다.

## 3. 용어 정리

이 대화에서 헷갈렸던 용어를 아래처럼 확정했다.

**고유 자원 강화 공격**

* 캐릭터 고유 자원을 소모해 쓰는 강화 공격/강화 스킬
* 개인 클래스 기믹
* 예: 표식 스택을 모아 소모하는 강화 공격

**오의**

* 오의 게이지 100%로 발동하는 캐릭터별 개인 궁극기
* 플레이어가 직접 입력해서 사용

**체인 버스트**

* 여러 플레이어가 일정 시간 안에 오의를 연계했을 때 자동 발동하는 팀 연계 효과
* 별도 수동 입력 스킬이 아님
* 2인 / 3인 / 4인 연계에 따라 효과 강화

**Break**

* 보스 무력화 상태
* 최대 딜타임
* 오의와 체인 버스트 최적 구간

**Burst Aura**

* 보스 특수 강화 상태
* 방어력 상승
* 오의 스킬이 성립하지 않음
* 체인 버스트 연계 불가
* 생존/대응/약점 공략 중심으로 넘겨야 하는 국면

즉 앞으로는 `고유 자원 강화 공격 / 오의 / 체인 버스트 / Break / Burst Aura` 를 분리해서 사용한다.

## 4. 한 판 게임 루프

한 판 루프는 다음으로 확정했다.

전초기지 대기 → 방장의 퀘스트 선택 → 파티 준비 완료 → 인스턴스 스테이지 진입 → 일반 전투 → 협동 목표 수행 → 보스전 → 결과/보상 화면 → 재도전 또는 전초기지 복귀

중요한 점:

* 전초기지는 실제 파티원이 같이 보이는 허브 맵
* 방장이 NPC를 통해 레이드/퀘스트를 선택
* 파티원은 준비 완료 상태를 표시
* 이후 인스턴스 맵으로 이동
* 클리어 후 보상은 NPC가 주는 게 아니라 결과/보상 화면에서 바로 지급
* 그 후 재도전 or 전초기지 복귀를 선택

## 5. MVP 범위

MVP는 한 판 버티컬 슬라이스다.

### 확정된 MVP

* 4인 협동 PvE 레이드
* 플레이어 캐릭터 1종
* 빌드 분기 2개
* 허브(전초기지) 1개
* NPC 1명
* 퀘스트 1개
* 스테이지 1개
* 일반 몬스터 1종
* 보스 1종

### 전투 시스템 MVP

* 기본 공격
* 근접 메인 / 원거리 보조 전환
* 회피 / 가드 / 패링
* HP / 스태미나 / 오의 게이지 / 고유 자원
* 오의
* 체인 버스트
* 보스 상태 사이클
   * Mode
   * OverDrive
   * Burst Aura
   * Break

### 전투 전 준비 MVP

* 액티브 스킬 로드아웃 4칸
* 장비
   * 무기 1
   * 보조 장비 1
   * 룬/진 2~3
* 회복 아이템 2종
* 소형 성장 트리

> **정정 (2026-11-11):** 장비는 '무기 1 + 보조 무기 1'이 아니라 **묶음 무기 세트 1개 + 룬/진 2~3**이다. 보조 장비 슬롯은 없다 — [6-7](#6-7-장비--룬-구조) 정정 참고.

### 명확히 제외한 것

> **정정 (2026-11-11):** 아래는 제외가 아니라 **후순위**다. AI 활용으로 개발 속도가 나면 들어올 수 있다.

* 탈것
* 동료 AI
* 추가 직업
* 다수 스테이지
* 대형 인벤토리

* 진/룬 강화/합성

* 완전한 Dedicated Server 배포
* 실서비스 매칭

## 6. 5단계 최종 확정: 플레이어 구조 설계

> **정정 (2026-11-11):** 이 절은 **프로토타입 영웅 1명**(근접 메인 / 원거리 보조 전환형) 기준이다. 모든 영웅이 근접/원거리 전환형은 아니다 — 전환은 이 영웅의 특성이지 플레이어 공통 구조가 아니다.

### 6-1. 플레이어 클래스 정체성

플레이어는 근접 메인 / 원거리 보조 전환형 대응 액션 클래스다.

핵심 역할:

* 근접 전투로 지속 딜과 브레이크 기여
* 회피·가드·패링으로 보스 패턴 대응
* 원거리 보조 모드와 오의 게이지 운용으로 팀 체인 타이밍 창출

즉, 대응을 잘할수록 팀 전체 딜타임을 여는 클래스로 설계했다.

### 6-2. 전투 중 플레이어 구조

**기본 전투 루프**

근접 진입 → 기본 공격/스킬로 기여 누적 → 회피/가드/패링 대응 → 필요 시 원거리 전환으로 약점 견제/안전 딜 → 재진입 → Break/오의/체인 타이밍에 화력 집중

**자원 구조**

전투 중 자원은 4축이다.

1. HP
   생존 자원
2. 스태미나
   회피, 가드 유지, 일부 기동 행동에 사용
3. 오의 게이지
   일반 공격, 스킬 적중, 피격, 팀 전투 기여로 축적
   오의 스킬의 기반 자원
4. 고유 자원: 표식 스택
   이 클래스 전용 자원
   원거리 견제나 패링 성공으로 쌓이고, 고유 자원 강화 스킬에서 소비

즉:

* 오의 게이지 = 파티 협동 자원
* 표식 스택 = 클래스 고유 전투 자원

**방어 수단 역할**

* 회피: 생존, 위치 조정, 저위험 저보상
* 가드: 안정 대응, 정면 유지, 스태미나 소모
* 패링: 고위험 고보상, 브레이크 기여 증가, 표식 스택 획득 또는 추가 효과

**근접 / 원거리 전환**

전환은 무기 교체가 아니라 전투 모드 전환이다.

근접 모드

* 기본 상태
* 지속 딜
* 브레이크 기여
* 표식 스택 소비형 피니시 / 고유 자원 강화 공격

원거리 보조 모드

* 약점 견제
* 표식 부여/유지
* 안전 딜
* 특정 패턴 대응

원거리 모드는 독립 메인 딜 모드가 아니라 기회 창출용 보조 모드다.

### 6-3. 입력 구조

기본 입력 구조는 아래로 정리했다.

* 기본 공격
* 방어 입력
   * 짧게: 패링
   * 유지: 가드
* 회피
* 액티브 스킬 1
* 액티브 스킬 2
* 액티브 스킬 3
* 액티브 스킬 4
* 근접/원거리 전환
* 오의 스킬 발동
* 상호작용

주의:

* 가드와 패링은 같은 입력축
* 고유 자원 강화 스킬은 액티브 4칸 중 1칸이 되는 방식이 가장 자연스럽다고 정리했다

> **정정 (2026-11-11):** '근접/원거리 전환'은 **전환형 영웅 전용 입력**이다. 범용 입력으로 설계하지 않는다.

### 6-4. 스킬 구조

> **정정 (2026-11-11):** 코어 키트는 **확정이 아니라 예시**다. 수시로 바뀔 수 있다.

**코어 키트**

* 기본 공격 체인
* 회피
* 가드
* 패링
* 근접/원거리 전환
* 오의 사용
* 체인 버스트 연계 참여

**액티브 로드아웃**

액티브는 4칸 로드아웃.

추천 역할:

* 근접 주력기 1
* 기동/진입기 1
* 원거리 표식/약점 견제기 1
* 자원 소모형 스킬/보조기 1

즉,

* 코어 키트는 고정
* 전투 스타일은 4칸 로드아웃으로 조정

### 6-5. 전투 전 준비 구조

전투 전 준비 요소는 아래 4개로 확정했다.

1. 어빌리티 로드아웃
   * 액티브 4칸 선택
   * 기본 전투 키트는 고정
2. 장비
   * 무기 슬롯 1개
   * 보조 장비 슬롯 1개
   * 룬/진 슬롯 2~3개
   > **정정 (2026-11-11):** 무기 슬롯 = 묶음 무기 세트 1개. 보조 장비 슬롯은 없다 — [6-7](#6-7-장비--룬-구조) 정정 참고.
3. 회복 아이템
   * 퀵 슬롯형 2종
   * 전투 중 사용 가능
   * 대형 인벤토리 없이 전투용 소비 구조만 제공
4. 소형 성장 트리
   * 빌드와 성장 방향을 정하는 핵심 준비 시스템
   * 대형 자유 트리가 아니라 소형 선택형 트리

### 6-6. 빌드 구조

빌드는 직업 1개 + 소형 트리 기반 분기다.

**트리 운영 원칙**

* 공통 기초 노드
* 갈림길 선택 노드
* 선택 후 심화 노드
* 핵심 특성 노드

즉, 공통 성장 + 일부 배타 선택 + 선택 후 심화 투자

**트리 카테고리 4개**

1. 공격 트리
   * 지속딜 vs 고유 자원 강화 스킬 강화
   * 근접 주력기 강화
   * 표식 대상 추가 피해
   * Break 중 피해 증가
2. 대응 트리
   * 회피 강화 vs 가드/패링 강화
   * 완벽 회피 보너스
   * 가드 스태미나 효율
   * 패링 성공 보상 강화
3. 브레이크·연계 트리
   * 브레이크 기여 증가
   * 오의 게이지 수급 강화
   * 체인 버스트 보상 강화
   * Full Chain 추가 효과
4. 고유 기믹 트리
   * 표식 스택 관련 강화
   * 원거리 표식 지속 강화
   * 근접 복귀 피니시 강화
   * 클래스 고유 패시브 해금

**대표 빌드 2개**

빌드 A: 패링 브레이커

* 패링 성공 보상 강화
* 브레이크 기여 증가
* 근접 자원 소모 스킬 강화
* 정면 대응형

빌드 B: 기동 마커

* 회피/기동 강화
* 원거리 표식/견제 강화
* 체인 버스트 지원 강화
* 안정적 기회 창출형

### 6-7. 장비 / 룬 구조

장비는 대형 수집 RPG식이 아니라 빌드 보정용 최소 구조다.

**MVP 장비 구조**

* 무기 1개
* 보조 장비 1개
* 룬/진 2~3개

**룬/진 예시 효과**

* 패링 성공 시 브레이크 기여 증가
* 표식 지속시간 증가
* Break 중 피해 증가
* 오의 게이지 획득량 증가
* 회복 아이템 효율 증가

즉, 룬은 장착형 modifier 시스템이다.

> **정정 (2026-11-11):** 원문의 '무기 1개 / 보조 장비 1개'를 무기와 보조 무기 한 개씩으로 읽지 않는다. 무기는 **묶음 무기 세트 1개**다.
>
> * 전환형 영웅만 세트 안에 무기 종류가 두 개(근접 · 원거리)다. 전환하지 않는 영웅의 세트는 무기 한 종류다
> * 장비 강화는 세트 단위다 — 강화하면 세트의 두 무기에 모두 효과가 적용된다
> * 무기 세트 말고 별도 장비 슬롯은 없다 — MVP 장비 = 묶음 무기 세트 1 + 룬/진 2~3
>
> 현재 구현과의 차이는 [부록 A](#부록-a-구현으로-달라진-점-2026-09-16-기준) 끝.

## 7. 6단계 최종 확정: 콘텐츠 구조 설계

### 7-1. 콘텐츠 목표

콘텐츠는 전초기지에서 파티를 구성하고, 방장이 퀘스트를 선택한 뒤 인스턴스 전투 맵에 진입해 일반 전투와 협동 목표를 수행하고, 보스의 상태 사이클과 약점/강공격/Burst Aura 기믹에 대응하여 클리어하는 4인 협동 PvE 레이드다.

핵심 루프:

* 전초기지 집합
* 파티 준비
* 인스턴스 진입
* 일반 전투
* 협동 목표
* 보스전
* 결과/보상
* 재도전 or 복귀

### 7-2. 전초기지 구조

전초기지는 실제 파티원이 허브 맵에 함께 보이는 구조다.

가능한 행동:

* 파티원들이 같은 공간에 표시
* 방장이 NPC를 통해 레이드 선택
* 각자 빌드/장비/로드아웃 정비
* 각자 준비 완료 표시
* 조건 충족 시 인스턴스 맵으로 이동

즉 퀘스트는 개인 일지형보다 파티 세션의 현재 출전 콘텐츠 선택에 가깝다.

### 7-3. NPC 구조

NPC는 레이드 운영 담당자다.

역할:

* 레이드/퀘스트 선택 인터페이스
* 스테이지 및 보스 브리핑
* 출발 조건 확인
* 인스턴스 진입 시작점 제공

주의:

* 클리어 후 보상은 NPC가 주지 않는다
* 보상은 결과/보상 화면에서 직접 제공된다

### 7-4. 퀘스트 구조

퀘스트는 단일 토벌 임무다.

흐름:

1. 전초기지에서 방장이 퀘스트 선택
2. 레이드 목표 브리핑
3. 인스턴스 진입
4. 일반 몬스터 구간 돌파
5. 협동 목표 수행
6. 보스방 개방
7. 보스 처치
8. 결과/보상 확인
9. 재도전 or 복귀

성격: 토벌 + 장치 활성화 + 최종 보스 제압

### 7-5. 스테이지 구조

스테이지는 전초기지와 분리된 인스턴스 전투 맵 1개다.

콘셉트: 봉인된 유적 전투 구역

구간 구성:

1. 진입 구역
   * 첫 일반 몬스터 조우
   * 전투 리듬 적응
   * 오의 게이지 축적 시작
2. 협동 목표 구역
   * 일반 몬스터 처리
   * 봉인 장치/제어 장치 2개 활성화
   * 보스방 개방 조건 충족
3. 보스 구역
   * 보스 조우
   * 상태 사이클 기반 레이드 전투
   * 클리어 후 결과 화면 진입

즉: 진입 → 전투 → 협동 목표 → 보스전

### 7-6. 일반 몬스터 구조

일반 몬스터는 근접 압박형 수호병 1종.

역할:

* 회피/가드/패링 기초 연습
* 근접/원거리 전환 사용 이유 제공
* 오의 게이지 사전 축적
* 협동 이동 구간 전투 압박

기본 패턴:

* 기본 연타
* 짧은 돌진
* 가드 가능한 공격
* 패링 가능한 강공격 1종
* 약점 노출 가능한 동작 1종

### 7-7. 보스 구조

보스는 봉인된 유적의 대형 수호체 1종.

요구하는 시스템:

* 강공격 전조 대응
* 약점 부위 공략
* Burst Aura 대응
* Break 딜타임 활용
* 회피·가드·패링·원거리 표식·오의 운영 전부

### 7-8. 보스 상태 구조

보스 상태 흐름:

* 기본 상태
* Mode 상승
* OverDrive
* Burst Aura
* Break

MVP 구현에서는 OverDrive 중 특정 조건에서 Burst Aura 진입 형태로 단순화 가능.

각 상태 의미

기본 상태

* 일반 패턴
* 딜 누적과 오의 게이지 축적
* 약점 공략 준비 단계

Mode 상승

* 보스 압박 증가
* 강화 전조
* 오의 사용 타이밍 고민 구간

OverDrive

* 공격성 증가
* 패턴 강화
* 생존과 대응 비중 상승

Burst Aura

* 일시적 특수 강화 상태
* 방어력 상승
* 오의 스킬 무효
* 체인 버스트 불가
* 대응·생존·약점 공략으로 넘겨야 하는 국면

Break

* 보스 무력화
* 약점 완전 노출
* 최대 딜타임
* 오의 및 체인 버스트 최적 구간

### 7-9. 보스 핵심 기믹

1. 강공격 전조
   * 붉은 이펙트 등 명확한 텔레그래프
   * 회피 / 가드 / 일부는 패링 요구
2. 약점 부위
   * 원거리 보조 모드로 견제 가능
   * 표식 부여와 연결 가능
   * 특정 약점 공략 시 브레이크 기여 또는 효율 증가
   * Break 중 더 명확히 노출
3. Burst Aura 대응
   * 오의 및 체인 연계 불가
   * 생존/약점 대응 중심
   * 플레이어에게 자원 사용 판단을 요구

### 7-10. 보스 패턴 구성

MVP 기준 5종 패턴:

1. 기본 근접 연타
2. 강공격 전조 패턴
3. 광역 패턴
4. 약점 노출 패턴
5. Burst Aura 진입 패턴

### 7-11. 결과 구조

클리어 후에는 결과/보상 화면이 먼저 나온다.

표시/기능:

* 클리어 결과
* 보상 표시 및 지급
* 기여도 요약 표시 가능
* `재도전` 또는 `전초기지 복귀`

중요:

* 보상은 NPC를 거치지 않는다
* 전투 종료 흐름 안에서 바로 제공

## B. 현재까지 프로젝트 설계 확정 요약

**프로젝트 한 줄 정의**

4인 협동으로 스테이지를 돌파하며 보스의 브레이크와 팀 체인 버스트를 활용해 화력을 집중하는 3인칭 PvE 액션 레이드

**코어 전투 판타지**

플레이어는 일반 공격과 회피·가드·패링·원거리 전환으로 전투 기여와 오의 게이지를 축적하고,
보스의 상태 사이클에 대응하며 유리한 타이밍에 오의와 체인 버스트를 연계해 합동 화력을 집중한다.

**플레이어 클래스 방향**

> **정정 (2026-11-11):** 아래는 프로토타입 영웅 기준이다. 전환 입력은 전환형 영웅 전용, 코어 키트는 예시, 장비는 묶음 무기 세트 — 위 6절 정정 참고.

* 근접 메인 / 원거리 보조 전환형 대응 액션 클래스
* 회피 / 가드 / 패링
* HP / 스태미나 / 오의 게이지 / 고유 자원(표식 스택)
* 액티브 로드아웃 4칸
* 고유 자원 강화 스킬 존재
* 오의는 개인 궁극기
* 체인 버스트는 여러 명의 오의 연계 결과 자동 발동

**빌드 구조**

* 직업 1개
* 대표 빌드 2개
   * 패링 브레이커
   * 기동 마커
* 소형 성장 트리 기반 분기
* 전투 전 준비 구조:
   * 어빌리티 로드아웃
   * 장비
   * 룬/진
   * 회복 아이템
   * 소형 성장 트리

**한 판 루프**

전초기지 대기 → 방장의 퀘스트 선택 → 파티 준비 완료 → 인스턴스 맵 진입 → 일반 전투 → 협동 목표 → 보스전 → 결과/보상 화면 → 재도전 또는 전초기지 복귀

**전초기지 구조**

* 실제 파티원이 같은 허브 맵에 보임
* 방장이 NPC를 통해 레이드 퀘스트 선택
* 각자 준비 완료 상태 표시
* 전원 준비 완료 후 방장 시작 또는 자동 시작
* 인스턴스 맵으로 이동

**NPC 역할**

* 레이드/퀘스트 선택 인터페이스 제공
* 스테이지/보스 브리핑
* 출발 조건 확인
* 인스턴스 진입 시작점 제공

주의: 보상은 NPC가 주지 않는다.

**결과 구조**

* 스테이지 종료 직후 결과/보상 화면 표시
* 보상 즉시 지급/표시
* 이후 `재도전` 또는 `전초기지 복귀`

**스테이지 구조**

* 봉인된 유적 전투 구역 1개
* 일반 몬스터 1종
* 협동 목표 1개
* 보스 1종

**일반 몬스터**

* 근접 압박형 수호병
* 회피/가드/패링/원거리 표식 연습용

**보스**

* 대형 수호체형 보스
* 상태 구조:
   * 기본 상태
   * Mode 상승
   * OverDrive
   * Burst Aura
   * Break

**Burst Aura 정의**

* 방어력 상승
* 오의 스킬 무효
* 체인 버스트 불가
* 대응/생존/약점 공략 중심 국면

**Break 정의**

* 보스 무력화
* 최대 딜타임
* 오의와 체인 버스트 최적 구간

## C. 용어 고정

앞으로 아래 용어로 통일해서 대화해야 한다.

* 고유 자원 강화 공격: 표식 스택 같은 클래스 고유 자원을 소모해 쓰는 강화 기술
* 오의: 플레이어가 직접 쓰는 캐릭터별 궁극기

* Burst Aura: 오의/체인 불가 특수 강화 상태

# 2부. MVP 마일스톤 계획 (M1 ~ M8)

> 4인 협동 PvE 레이드 MVP를 뚫는 개발 순서. 각 마일스톤은 "검증 가능한 단일 목표"를 갖도록 쪼갰고, 앞 마일스톤이 뒤 마일스톤의 기반이 되도록 설계했다.

## 설계 원칙

### 마일스톤 쪼개기 기준

1. **각 마일스톤 끝에서 플레이 가능한 상태가 된다** — 최소한 "여기까지 하면 이런 식으로 돌아간다"가 보여야 함
2. **핵심 리스크를 앞쪽 마일스톤에서 터뜨린다** — 나중에 가서 "이거 안 되네"가 나오면 이미 늦음
3. **각 마일스톤은 이전 마일스톤 위에 얹힌다** — 버리는 작업 최소화

### "확장 포인트 예약" 원칙

앞 마일스톤에서 뒤 마일스톤의 요구를 **모두 고려해 구현**할 필요는 없지만, **확장 가능한 구조**는 미리 깔아둬야 한다.

핵심: **Modifier 레이어만 예약**하고 실제 수정 주체는 해당 마일스톤에서 만든다.

- 전투 스탯은 Attribute로, 데미지 계산은 GE로 구성 (GAS 기본)
- 기본값(1.0)인 Multiplier Attribute들을 **미리 만들어둠**
- 예: `IncomingDamageMultiplier`, `OutgoingDamageMultiplier`, `BreakContributionMultiplier`, `UltGainMultiplier`
- 나중에 빌드/룬/상태 효과 등이 **이 Multiplier만 건드리면 되는** 구조

이 원칙을 지키면:

- 앞 마일스톤에서 "상상으로 빌드 시스템 설계" 안 해도 됨
- 뒤 마일스톤에서 "기존 전투 코드 갈아엎기" 안 해도 됨
- 구조는 확장 가능하되 구현 속도는 유지

### 네트워크 테스트 3단계 (M1 이후 모든 마일스톤에 상시 적용)

각 마일스톤 종료 시 다음 3단계를 순서대로 통과시킨다.

| 단계 | 설정 | 목적 |
| --- | --- | --- |
| 1단계 | Listen Server + Run Under One Process | 로직 검증 (빠른 디버깅) |
| 2단계 | Listen Server + Separate Process | 실제 네트워크 재현 (복제/RPC 타이밍) |
| 3단계 | Client + Separate Process | Dedicated 호환성 검증 |

3단계 통과 = 그 마일스톤은 Dedicated로도 돌아간다고 간주.

> 3단계의 실제 구성(별도 데디 서버 프로세스)은 [부록 B](#부록-b-네트워크-3단계-실행-매트릭스-2026-09-16-기준)의 정정을 따른다.

## 마일스톤 전체 지도

| 마일스톤 | 목표 | 예상 기간 |
| --- | --- | --- |
| **M1** | 서버 골격 (세션 + Travel + 페이로드) | 1주 |
| **M2** | 전투 프레임 (단일 캐릭터) | 1~2주 |
| **M3** | 협동 전투 (일반 몬스터) | 1~2주 |
| **M4** | 오의 + 체인 버스트 | 2주 |
| **M5** | 보스 상태 사이클 | 2~3주 |
| **M6** | 콘텐츠 루프 (협동 목표 + 결과) | 1~2주 |
| **M7** | 빌드 / 장비 / 성장 트리 | 2~3주 |
| **M8** | 최종 Dedicated 검증 (상시 + 최종) | 상시 + 1주 |

> 기간은 대략치이며 실제 진행 상황에 따라 유연하게 조정. 앞 마일스톤이 예상보다 빠르게 끝나면 다음 마일스톤을 조금 더 깊게 파고, 반대로 늦어지면 범위를 줄인다.

### M1 / M2 병행 진행 방침

M1과 M2는 **선형 진행이 아닌 유동 병행**으로 진행한다.

- **M2 부분 구현 (1~2주)**: CombatTestMap 싱글 환경에서 전투 골격 먼저 확보
- **M1 구현 (1주)**: 전투가 어느 정도 올라온 상태에서 Travel + 페이로드 파이프라인 구축
- **통합 테스트**: M2 캐릭터를 M1 위에 얹고 3단계 네트워크 테스트 통과

M2를 먼저 잡는 이유:

- CombatTestMap 싱글 환경이 전투 로직 디버깅에 훨씬 쉬움
- M1만 먼저 만들면 "이동은 되는데 검증할 게 없음" 상태
- M2가 준비된 상태에서 M1을 테스트해야 페이로드 복원이 **실제 데이터로** 검증됨

## M1. 서버 골격 (세션 + Travel + 페이로드)

**예상 기간**: 1주 (M2 부분 구현 후 시작)

### 목표

HubMap ↔ RaidMap SeamlessTravel과 GameInstance 페이로드 전달 파이프라인을 확보한다.

### 포함 범위

- HubMap / RaidMap 기본 구조
- SeamlessTravel로 Hub → Raid → Hub 전환
- GameInstance / Subsystem 기반 페이로드 보관 / 복원
- 최소 접속 테스트 (더미 캐릭터 또는 M2에서 만든 캐릭터)

### 검증 리스크

- Listen Server 기반 + 페이로드 전달이 의도대로 동작하는가
- SeamlessTravel 중 PlayerController / PlayerState 재생성 타이밍
- InitState 체인과 Travel 타이밍의 정합성

### 종료 조건

- 4인이 HubMap에 접속
- RaidMap으로 이동
- HubMap 복귀
- 이동 전후 페이로드 데이터(더미라도 OK) 복원 확인
- 네트워크 3단계 테스트 통과

### 확장 포인트 예약

- **페이로드 구조 확장성**: 현재는 플레이어 ID 정도만 들어가도 OK. 단, **USTRUCT로 정의**하고 필드 추가가 용이한 형태로. M4(오의/체인 연계용 식별자), M7(빌드/룬/로드아웃)이 이 구조에 얹힘
- **전달 계층 교체 가능성**: GameInstance 메모리 전달로 구현하되, "페이로드 구성 → 전달 → 복원"이 **별도 함수/클래스로 분리**되도록. 장기적으로 URL options나 매치메이커로 교체 가능해야 함 (→ 서버 구조 설계 문서 참조)

## M2. 전투 프레임 (단일 캐릭터)

**예상 기간**: 1~2주 (M1보다 먼저 부분 구현 시작)

### 목표

CombatTestMap 싱글 환경에서 캐릭터의 전투 골격을 확보한다. "전투가 돌아가긴 한다" 수준이 목표이며, 밸런스/디테일은 이후 마일스톤에서.

### 포함 범위

- 캐릭터 이동 (CMC)
- 기본 공격 체인
- 방어 3종: 회피 / 가드 / 패링
- 근접 ↔ 원거리 모드 전환
  > **정정 (2026-11-11):** 프로토타입 영웅(전환형) 기준. 전환은 영웅별 특성이라 범용 입력 · 공통 구조로 만들지 않는다.
- 자원 4축:
    - HP (생존 자원)
    - 스태미나 (회피/가드 소비)
    - 오의 게이지 (축적만, 사용은 M4)
    - 표식 스택 (누적만)

### 검증 리스크

- GAS + CMC 위에서 자원 4축과 모드 전환이 자연스럽게 돌아가는가
- 패링의 짧은 윈도우 처리
- 근접/원거리 전환 중 입력 처리
- 싱글 환경에서도 **멀티플레이 전제 코드**로 짜는 습관

### 종료 조건

- 더미 타겟 하나 놓고 기본 공격 3단 체인 → 회피 → 가드 → 근/원 전환이 **싱글에서 어색하지 않게** 돌아감
- 자원 4축이 의도대로 변동
- 밸런스, 애니메이션 디테일, 이펙트는 이후 마일스톤으로 미룸

### 확장 포인트 예약

- **Multiplier Attribute 미리 생성 (기본값 1.0)**:
    - `IncomingDamageMultiplier` / `OutgoingDamageMultiplier`
    - `BreakContributionMultiplier`
    - `UltGainMultiplier` (M4에서 사용)
    - `StaminaRecoveryMultiplier` / `StaminaCostMultiplier`
- **데미지 계산 GE**가 이 Multiplier들을 곱하는 공식으로 구성 — 나중에 Modifier만 갈아끼우면 빌드/룬/상태 효과가 자연스럽게 얹힘
- **CMC 확장 가능성**: 이동 속도 base값 + Modifier 구조 (Sprint, WallRun이 곱하는 구조). 빌드의 "이동 속도 +10%"도 같은 레이어에 얹힘
- **싱글 구현이지만 Replicated / ReplicatedUsing / SavedMove / NetworkMoveData 전제**: 나중에 멀티 붙일 때 뒤집기 어려움. 처음부터 잘 잡기

### 진행 방침

- **M1보다 1~2주 먼저 시작 (Phase A)**
- CombatTestMap 싱글 환경
- "조금만 더 다듬으면"에 빠지지 않도록 **종료 조건 도달하면 M1으로 넘어감**
- M1 작업 중 M2에서 수정하고 싶은 게 생겨도 메모만, 통합 테스트(Phase C) 때 같이 정리

## M3. 협동 전투 (일반 몬스터)

**예상 기간**: 1~2주

### 목표

M1+M2 통합된 기반 위에서, 일반 몬스터와 싸우는 멀티 전투가 정상 동작하는지 검증한다.

### 포함 범위

- 일반 몬스터 1종 (근접 압박형 수호병)
- 기본 AI: 접근 / 공격 / 피격 반응
- 패턴: 기본 연타 / 짧은 돌진 / 가드 가능 공격 / 패링 가능 강공격 / 약점 노출 동작
- 어그로 관리 (멀티 환경에서 타겟 선정)
- 피격 / 데미지 처리 서버 권한
- 몬스터 상태(위치, HP, 사망) 복제

### 검증 리스크

- 멀티 환경에서 **회피/가드/패링 타이밍**이 레이턴시와 맞물려 어색하지 않은지
- **데미지 판정의 서버 권한 처리**가 의도대로
- 몬스터 상태 복제 누락 없음
- SoulForged 경험이 있어 상대적으로 안정적인 구간

### 종료 조건

- 4인이 붙어서 몬스터 여러 마리를 처치 가능
- 3단계 네트워크 테스트 통과

### 확장 포인트 예약

- **몬스터 스탯도 Attribute 기반**: 나중에 스테이지 난이도 조정 / 보스 공유 구조로 확장 가능
- **어그로 가중치 Modifier 방식**: 도발 스킬, 탱커 메커니즘 등이 추후 얹힐 수 있도록
- **풀링 가능성**: MVP에선 풀링 없어도 되지만, 스폰/디스폰 인터페이스를 분리해두면 SoulForged의 Object Pooling 경험을 나중에 이식 가능

> M3 구현 방향 메모는 [부록 C](#부록-c-m3-구현-방향-메모-2026-09-16-기준), 구현 설계는 [m3-enemy-ai.md](m3-enemy-ai.md), 착수 전 검토는 [부록 D](#부록-d-2026-11-11-착수-전-검토-메모).

## M4. 오의 + 체인 버스트

**예상 기간**: 2주

### 목표

이 프로젝트의 핵심 판타지 중 "다 같이 터뜨린다" 부분을 실현한다.

### 포함 범위

- 오의 발동 (캐릭터별 개인 궁극기)
- 오의 게이지 수급 로직 (일반 공격 / 피격 / 기여도)
- **체인 버스트**: 여러 플레이어의 오의가 짧은 시간 안에 연달아 발동되면 자동 발동
- 2인 / 3인 / 4인 연계별 효과 강화
- 체인 윈도우 UI (연계 가능 표시)

### 검증 리스크

- **여러 플레이어의 오의 발동을 서버가 수집하고 윈도우를 판정**하는 로직
- 체인 버스트가 정확히 N명 연계로 판정되는가 (race condition 주의)
- 레이턴시 차이 환경에서 판정 공정성
- **윈도우 길이**는 구현하면서 튜닝 (초기값은 임의로 잡고 테스트)

### 종료 조건

- 더미 타겟 상황에서 4인 체인 버스트까지 정상 연계
- 3단계 네트워크 테스트 통과

### 확장 포인트 예약

- **오의 발동 여부가 외부 요인으로 차단 가능한 훅**: M5의 Burst Aura 차단이 여기 얹힘. 오의 GA의 CanActivate에서 외부 상태를 참조할 수 있는 구조
- **체인 버스트 기여도 Multiplier Attribute**: M7 빌드에서 "체인 버스트 보상 강화" 특성이 얹힘
- **게이지 수급률 Multiplier**: M7 빌드의 "오의 게이지 획득량 증가" 룬이 얹힘

## M5. 보스 상태 사이클

**예상 기간**: 2~3주

### 목표

보스 전투의 국면 전환 구조가 동작한다.

### 포함 범위

- 보스 1종 (대형 수호체)
- 상태 머신: 기본 → Mode 상승 → OverDrive → Burst Aura → Break
- **Burst Aura 중 오의 차단 처리** (시도는 되지만 서버가 거절)
- **Break 중 최대 딜타임** (약점 노출 / 피해 증가)
- 패턴: 최소 3종 (기본 연타 / 강공격 전조 / 약점 노출), 여유 되면 5종 (광역 / Burst Aura 진입 추가)

### 검증 리스크

- Burst Aura 중 오의 시도 시 **UX 처리** (입력 받았지만 거절됨을 어떻게 클라에 보여줄지)
- 상태 전환 타이밍의 서버-클라 동기화
- Break 중 피해 증가 배율 적용

### 종료 조건

- 4인이 보스를 잡아 전 상태 사이클을 한 번 돌려봄
- Burst Aura에서 오의 차단이 UX 포함해 자연스럽게 처리됨
- 3단계 네트워크 테스트 통과

### 확장 포인트 예약

- **보스에 대한 추가 피해 Multiplier**: M7 빌드에서 "Break 중 피해 증가" 특성이 얹힘
- **패턴 확장 가능**: 3종으로 시작해서 여유 되면 5종까지. 패턴 데이터는 DataAsset / DataTable 기반으로 해서 추가 용이하게
- **상태 전환 조건**: 현재 HP 비율 기반으로 단순하게 가되, 조건이 복잡해질 수 있으므로 **조건 평가 로직을 상태 머신 외부로 분리**

## M6. 콘텐츠 루프 (협동 목표 + 결과)

**예상 기간**: 1~2주

### 목표

한 판 루프가 처음부터 끝까지 돌아간다.

### 포함 범위

- 진입 구역 → 협동 목표 구역 → 보스방 개방 → 보스전 → 결과 화면
- 협동 목표: 봉인 장치 / 제어 장치 2개 활성화
- 결과 화면: 클리어 결과 / 보상 지급 / 재도전 / 복귀
- 재도전: RaidMap 재진입
- 복귀: HubMap으로 SeamlessTravel

### 검증 리스크

- **Result 상태 전환** (맵 이동 없이 상태만 바꾸는지, 별도 처리인지)
- 재도전 시 파티 상태 유지
- 복귀 시 Hub에서 파티 / 로드아웃 복원

### 종료 조건

- 4인이 HubMap에서 시작해서 한 판 클리어하고 Hub로 돌아올 수 있음
- 재도전 플로우 동작
- 3단계 네트워크 테스트 통과

### 확장 포인트 예약

- **보상 지급 구조**: MVP에선 하드코딩으로 지급해도 OK, 단 "보상 테이블" 구조를 참조하는 형태로 구성해서 나중에 확장 가능
- **결과 통계**: 기여도 요약 등은 MVP 제외, 그러나 GameState에 기본 집계 변수는 미리 두면 나중에 표시만 추가

## M7. 빌드 / 장비 / 성장 트리

**예상 기간**: 2~3주

### 목표

전투 전 준비 시스템 완성. 두 대표 빌드를 실제로 플레이 가능하게.

### 포함 범위

- 액티브 로드아웃 4칸 선택
- 장비: 무기 1 / 보조 1 / 룬 2~3
  > **정정 (2026-11-11):** 장비 = 묶음 무기 세트 1개(전환형 영웅만 두 종류) + 룬 2~3, 보조 장비 슬롯 없음. 강화는 세트 단위로 두 무기에 모두 적용 — 1부 6-7 정정 참고.
- 회복 아이템 2종 (퀵 슬롯)
- 소형 성장 트리 4카테고리:
    - 공격 트리
    - 대응 트리
    - 브레이크·연계 트리
    - 고유 기믹 트리
- 대표 빌드 2개:
    - 패링 브레이커 (정면 대응형)
    - 기동 마커 (안정적 기회 창출형)
- HubMap에서 설정 → 페이로드로 전달 → RaidMap에서 적용

### 검증 리스크

- **빌드 변경이 실제 전투에 영향**을 주는지 (M2~M5에서 예약해둔 Multiplier들이 실제로 반영되는지)
- 페이로드 구조 확장이 무리 없이 되는지
- 룬 장착이 서버 권한으로 처리되는지

### 종료 조건

- 두 빌드를 각각 플레이해봤을 때 **플레이 감각이 확연히 다름**
- 3단계 네트워크 테스트 통과

### 세부 설계 보류 항목

- **성장 트리 카테고리당 노드 수**: 이 마일스톤 진입 시점에 상세 설계. 대략 3~5노드 예상하나 확정 아님
- 구체 특성 효과 수치는 구현하면서 튜닝

### 이전 마일스톤 덕분에 쉬워지는 점

M2~M5에서 **Multiplier Attribute + GE 기반 Modifier 레이어**를 예약해둔 덕분에, M7은 다음만 하면 됨:

- 트리 특성 / 룬 / 장비가 얹을 **GE 또는 Effect 정의**
- 이 GE를 페이로드 반영 시점에 적용하는 로직
- UI로 선택 / 표시

기존 전투 코드를 뜯을 일이 거의 없음.

# 부록 A. 구현으로 달라진 점 (2026-09-16 기준)

> 옛 계획 파일 `4-pve-floofy-mochi.md` 의 '기획 확정 사항 — 변경점만' 절을 대화 기록(`804c35fc…jsonl`)에서 복원했다. 그 뒤(락온 · 원거리 사격 · 애니)로 바뀐 것은 반영돼 있지 않다.

원문의 **장르 · 코어 전투 판타지 · 용어(고유 자원 강화 공격 / 오의 / 체인 버스트 / Break / Burst Aura) · 한 판 루프**는 그대로 유효하다. 구현으로 확정되며 달라진 것만:

- **캐릭터 1종** 유지. 단 `UAstralCharacterDefinition`(메시·AnimBP·`CombatPawnData` 자리) 구조로 구현돼 **N종 확장이 데이터 작업**이 됐다
- **장비**: 원문 "무기 1 / 보조 1 / 룬 2~3" 중 **무기만 구현**. 계열(Family) 2종(근접·원거리) × 변형(Definition) 구조. 보조·룬은 M7
- **전투 모드 전환**: "무기 교체가 아닌 모드 전환"이라는 원문 정의 유지. 내부 구현은 **두 무기 동시 장착 + 활성 스왑**(`StyleCycle` 순환)이라 플레이어 경험은 원문대로 즉시 전환
- **한 판 루프**: `전초기지 → 퀘스트 선택 → 준비 → 인스턴스 진입`까지 구현. 이후(일반 전투 · 협동 목표 · 보스전 · 결과/보상)는 M3~M6
- **구현 용어 추가**: 계열(Family) / 변형(Definition) / 로드아웃(Loadout) / 전투 스타일(CombatStyle)

**2026-11-11 정정과 현재 코드:**

- **전환형이 아닌 영웅:** 구조는 이미 영웅별로 돼 있다. `UAstralPawnData::InitialCombatStyle` 이 빈 태그면 그 폰은 스타일 시스템을 쓰지 않고(주석: "스타일을 쓰는 히어로만 지정"), 전환 GA `UAstralGA_Hero_SwitchCombatStyle` 은 히어로별 BP 의 `StyleCycle` 데이터로 구성하며 "전환 없는 히어로는 이 GA를 부여받지 않는다"(헤더 주석). 입력 태그 `InputTag.SwitchCombatStyle` 는 남아도 GA 가 없으면 아무 일도 없다. 다만 전환형이 아닌 영웅을 실제로 만들어 돌려 본 적은 없다.
- **묶음 무기 세트:** 아직 없다. 지금은 근접 · 원거리 무기를 각각의 변형 정의(`UAstralWeaponDefinition`)로 따로 장착한다(`UAstralPawnData::DefaultEquipment` 배열). 세트라는 데이터 단위와 세트 단위 강화는 강화 시스템과 함께 M7 에서 다룬다.
- **보조 장비:** 정정 7로 슬롯이 없어졌다. 위 복원 원문의 "보조·룬은 M7" 중 M7 에 남는 건 룬뿐이다.

# 부록 C. M3 구현 방향 메모 (2026-09-16 기준)

> 옛 계획 파일의 '다음 — M3 협동 전투 (StateTree)' 절을 복원했다. 아래 원문 뒤에 2026-11-10 현재 상태를 붙였다.

**AI 프레임워크는 StateTree로 확정.** 근거: M5 보스 상태 사이클(기본→Mode 상승→OverDrive→Burst Aura→Break)이 명시적 상태 머신이라 **같은 프레임워크를 재사용**할 수 있고, 기획서의 *"상태 전환 조건 평가 로직을 상태 머신 외부로 분리"*가 StateTree의 조건 평가 모델과 맞는다.

### ⚠️ StateTree가 호출할 GA는 **단발**이어야 한다

앞선 계획서의 *"실제 공격은 기존 GA 호출 — TelegraphAttack이 이미 원형"* 은 모호했다. `AstralGA_Enemy_TelegraphAttack.cpp` 는 `OnSpawn`으로 발동해 **스스로 영구 공격 루프를 돈다**(`StartCycle` → 대기 → 텔레그래프 → 판정 → `StartCycle`). 이걸 StateTree가 호출하면 StateTree가 공격 시점과 회복 시간을 통제하지 못한다.

| | 역할 |
|---|---|
| 기존 `GA_Enemy_TelegraphAttack` | **더미 검증용으로 유지** (자체 루프 그대로) |
| 신규 실전 Enemy GA | **1회 실행** — 텔레그래프 → 판정 → 종료 |
| StateTree | 공격 선택 → GA 활성화 → **GA 종료 대기** → Recovery → 다음 판단 |

**첫 수직 단위** (여기까지가 한 덩어리):

```
AcquireTarget → Chase → SelectAttack → ActivateAbilityByTag → WaitAbilityEnd → Recovery
```

착수 순서:

- `StateTree` / `GameplayStateTree` 플러그인 활성화 + Build.cs 모듈 추가 (`AIModule`은 이미 있음)
- `AAstralAIController` + StateTree 자산 → 단일 타깃 · 접근 · **단발 공격 GA** · 피격/사망까지 먼저 완성
- **어그로는 AIController에 몰지 말고 서버 전용 `UAstralThreatComponent`로 분리** — `AddThreat` / `RemoveTarget` / `SelectBestTarget` / `ClearInvalidTargets`. 기획서의 "어그로 가중치 **Modifier 방식**"과도 맞는다
- 몬스터 몽타주 + 무기 트레이스 — `astral-ue-montage` 자동화 활용, 장비는 `AstralCombatCharacter`에 이미 지원됨
- **스폰/디스폰 인터페이스는 적 1종이 완성된 뒤 스포너를 붙이는 시점에 추출.** 기획서의 M3 확장 포인트 예약 항목이지만, 소비자가 하나뿐인 상태에서 먼저 만들면 실제 풀링 요구와 어긋날 가능성이 크다 — 예약 원칙과 YAGNI의 절충점

# 부록 D. 2026-11-11 착수 전 검토 메모

> M3 착수 전에 이 계획서를 런타임 코드와 대조한 결과다. **제안이며 확정이 아니다** — 원문과 정정을 바꾸지 않는다. 소스를 읽어 판단했고 실행한 것은 없다. 구현 쪽 상세는 [m3-enemy-ai.md](m3-enemy-ai.md) §0.

**방향은 유효하다.** StateTree · 단발 GA · 서버 전용 위협 컴포넌트라는 부록 C 의 방향과 2부의 예약 원칙은 지금 코드와 어긋나지 않는다. 예약 Multiplier 는 `IncomingDamageMultiplier` · `OutgoingDamageMultiplier` · `MoveSpeedMultiplier`(공용)와 `BreakContributionMultiplier` · `UltGainMultiplier` · `StaminaCostMultiplier` · `StaminaRecoveryMultiplier`(히어로)가 이미 있다.
